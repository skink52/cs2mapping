# Building original CS2 addons with an AI agent

How the original minigames were made: Hellmatch (Doom-style deathmatch, 4 arenas × 16), Space Racer (32-car anti-grav racer), mg_trenchwarfare
(WW1 trenches with mortars and biplanes), Puppet Brawl (2.5D fighter), mg_deku_tree (hollow-tree KZ with monsters) and a grid bomb-arena game.
Each one runs **entirely inside one map**: no server plugins, everything generated by Python tools and a cs_script.

Source repos (all MIT code): [hellmatch-cs2](https://github.com/skink52/hellmatch-cs2), [space-racer-cs2](https://github.com/skink52/space-racer-cs2),
[trenchwarfare-cs2](https://github.com/skink52/trenchwarfare-cs2), [cs2-fighter](https://github.com/skink52/cs2-fighter).
The reusable parts of their toolchains are collected in [`create/`](../../create).

Related: [models.md](models.md) (props, player models, rigs), [hud.md](hud.md) (Panorama HUD, overlays, loading screens, radar), [custom-weapons.md](custom-weapons.md),
[sound.md](sound.md), [workshop.md](workshop.md), [../reference/cs_script-notes.md](../reference/cs_script-notes.md), [../reference/cs2-gotchas.md](../reference/cs2-gotchas.md).

## 1. Project shape

```
src/core/     the game rules in plain JavaScript, no engine calls (runs in Node for tests and balance sims)
src/cs2/      the CS2 side: pawn parking + camera, input, prop-pool rendering, HUD, sounds, kills, round control, chat commands
tools/        Python generators: models, materials, textures, HUD, sounds, loading screens, radar, and the map writer
tools/build.mjs   concatenates src/core + generated data + src/cs2 into maps/scripts/<name>.js (and a Node test module)
test/         sim (bots on the pure game), mock engine (the real script on a stand-in API), tsconfig + point_script.d.ts
preview/      software renders for checking without CS2 (levels, models, HUD at 16:9/4:3/21:9, chase camera)
out/addon/    generated content tree -> content\csgo_addons\<addon>\     out/game/ -> game\csgo_addons\<addon>\
ref/          the Hammer map (as last saved by the user) the build writes into, stock files used as templates
```

- **Why split core and cs2:** the rules can be simulated thousands of times in Node (balance, durations, bot behaviour, regression hashes) and the
  CS2 adapter stays thin. Puppet Brawl ran 600 s × 3 seeds of CPU-vs-CPU per fighter to balance stats.
- The build bakes generated data (level geometry tables, model lists, HUD string indexes, music lengths) into the script as constants.
- One `CONFIG` object at the top of the script holds every tunable (round length, arena sizes, damage, cvars applied), so changes don't need code edits.

## 2. Writing the map without Hammer

- The map is a binary DMX `.vmap`. `create/dmx.py` reads and writes it losslessly; `create/vmaplib.py` writes entities, meshes and nodes;
  `create/vmesh.py` writes open meshes (boundary half-edges, as Valve's maps use). `tools/vmapedit.py` (porting side) does the same with
  keyvalues2 support.
- **Start from the user's map.** The generator takes the map as last saved in Hammer (`<X>_CURRENT_VMAP=` or argv) and layers its content on top, keeping
  the user's edits. A fresh project starts from the addon template map (keeps its sky, lighting, probes, post-processing, team intro, nav).
- **Tag everything generated** with a vis group (`tw_gen`, `fdm_env`) so a re-run replaces only its own work.
- Full regeneration can reshuffle randomly placed things once the user's edits act as obstacles (RNG cascade). For late changes, **patch the user's
  vmap** with a small delta script instead (`patch_vmap.py` style), so nothing moves.
- `create/check_mesh.py <vmap>` validates every half-edge mesh (opposites, next chains, face loops, vertex counts) before the user opens it.
  `tools/vmap_preview.py <vmap> out.png` renders a top-down and four corner views to check layout.

## 3. World layout conventions

- **Multi-arena maps:** every arena/level/track sits in its own box in the void. Each box is enclosed in a moondome (sky-material shell) with a
  `tools/skybox` shell 1 unit inside it for environment lighting. Several skies in one map = one moondome per box with its own sky material.
- **Vis hints:** Lowest over everything (the void), Low only over the playable band, Lower (`hintType` 8) for big volumes, Medium only around very complex
  meshes. Prop-only levels gain nothing from fine hints. Sky shells around sealed rooms: Exclude from Vis.
- **Lighting:** enough stationary lights that weapons aren't black; one `env_combined_light_probe_volume` per room/arena; lightmap resolution
  volumes (`toolslightmapres`) over the player space; probe-lit (not lightmapped) foliage and small props; ≤ 4 shadowed lights overlapping.
- **Lobby + pawn booth:** a lobby room with join pads/chat commands, a sealed booth where parked pawns wait, a model cache room with one hidden
  `prop_dynamic` per model the script will `SetModel` to, and a `func_nav_markup` WALKABLESEED for bots.
- **3D skybox** (mg_trenchwarfare): a separate `<map>_3dskybox.vmap` (`mapUsageType skybox`, own `light_environment`/`env_sky`, `sky_camera` scale 16) with a
  terrain ring continuing past the map edge; the main map gets a `skybox_reference`. Nothing reachable may be in it.
- **KZ maps:** `trigger_multiple` `timer_startzone` / `timer_endzone` and `info_teleport_destination` `timer_start` (the no-FGD convention timer plugins read).

## 4. The script

- **Instances/arenas:** one `Arena` object per arena, each ticked inside its own try/catch so one failure can't stop the others. Players are assigned
  per round; arena sizes follow a table (e.g. under 16 all in one, 16 → 8+8, 31 → 16+15, 32 → 8×4).
- **Rendering by prop pool:** everything that moves is a pooled `prop_dynamic` from a `point_template`, model swapped by `SetModel`, moved with `Move`
  every tick, colour/light via `SetColor`, skins for team colours. Effects are pooled with hard caps (dropped, never spawned unbounded).
- **Rounds:** script runs the round (`mp_ignore_round_win_conditions 1`), ends it with `FireWinCondition`, varies the mode each round (FFA / TDM /
  elimination / last man standing), spectating other arenas once yours ends, a time cap via `SetRoundRemainingTime`. Locked rounds (no joining mid-race)
  queue new players for the next round.
- **Kill credit:** real CS2 kills via `TakeDamage` with `FORCE_DEATH` so rank plugins count them; podium splits (winner 50% of the arena's kills, 2nd 30% …)
  for games without natural kills; team win from the top-N per team.
- **AFK and robustness:** AFK detection on input (not position), slot ownership checked once a second, full HUD reset on activate/team change, everything
  re-validated after round restarts.
- **Bots:** CS2 bots fill slots; the script drives them with its own AI (Space Racer's lane-keeping cut car contact 30%).
- **Performance:** see [cs_script-notes.md](../reference/cs_script-notes.md#performance). Measure on the mock engine before shipping.

Full API patterns: [../reference/cs_script-notes.md](../reference/cs_script-notes.md).

## 5. Assets

| Need | How | Tool |
|---|---|---|
| Props from downloaded models (Sketchfab etc.) | GLB → SMD + `csgo_complex` vmats + PNGs + convex hulls | `create/glb2cs2_multi.py` |
| Procedural props with baked PBR textures | Python geometry + procedural shaders baked to an atlas, LODs, hulls, turntable preview | `create/build_prop.py` + `bake/geo/shaders/noise/render.py` ([models.md](models.md#procedural-props)) |
| Props that use real CS2 textures | Charts mapped to stock Valve materials with real-scale UVs | `create/stock.py` |
| Voxel/sprite models | Carved from 2D sprites (8 rotations), lathed, extruded, or crossed planes | Hellmatch `tools/sprites.py`, Space Racer `tools/cars.py` |
| Player models from CS:GO | Rebuild onto the CS2 agent skeleton and setup | [models.md](models.md#player-models) |
| Animated characters | SMD rigs, mocap retargeting, clips per move | [models.md](models.md#animated-rigs) |
| Weapons | `weapons.vdata` override + rigged models | [custom-weapons.md](custom-weapons.md) |
| HUD, overlays, loading screens, radar | Panorama layout/css + generated images | [hud.md](hud.md) |
| Sounds and music | Synthesised (no samples) + vsndevts | [sound.md](sound.md) |
| Reading stock CS2 textures | VPK index + `vtex_c` decoder | `create/vpkdir.py`, `create/vtexread.py` |

Material basics: `csgo_complex` for lit PBR, `csgo_unlitgeneric` for flat/retro looks (Hellmatch's 4× nearest-neighbour upscaled textures keep the
point-sampled look), `csgo_vertexlitgeneric` + `F_SELF_ILLUM` for glowing parts, `csgo_static_overlay` for decals, `csgo_moondome` for sky shells.

## 6. Testing before CS2

1. `node test/sim.cjs` — the pure game with bots: durations, balance, crashes, regression hash of every state.
2. `node create/test/mock_point_script.mjs <script> entities.json players=32 seconds=600` — the real script on a stand-in engine (or the project's own richer mock).
3. `sh create/test/tscheck.sh <script>` — type check against Valve's API.
4. Software previews: model turntables, map views, HUD laid out like Panorama at 16:9, ultrawide and 4:3 with CS2's own HUD areas marked.
5. The user's in-game test: a short checklist. Assume every item passed unless the user says it failed.

## 7. Delivery

- The user keeps Hammer closed while files are written, and backs up the map. Always read the user's latest `.vmap` before generating.
- Send only changed files. Bulk files (animations, textures) go in zips under ~20 MB (25 MB+ uploads failed), with an unpack `.bat` that applies each zip once
  and never contains the user's `.vmap` or the live script.
- Compile: the map build in Hammer (first build compiles models, materials, sounds, HUD and script), or the command-line runner
  (`run_build.bat`). Script-only models and the script/HUD may need `resourcecompiler -f -i <file>`.
- Version string printed by the script on load (`v2.1.1`), so the user can confirm the new build is running.
- After in-game testing, record what was verified and what wasn't in the project notes (`NOTES.md`/`STATUS.md` in the repo).
